# Database backend

`source/backend/database` owns everything database-shaped: the Rust database foundation being built as the exclusive application access boundary for `mzizi` and `mzizi_operations`, the generated SQL migration releases, and — during transition — the legacy Bun TypeScript service. Design and status: [`.docs/design/data/DATABASE_FOUNDATION.md`](../../../.docs/design/data/DATABASE_FOUNDATION.md); layout decision: `.docs/decisions/DEC-DATABASE-FOUNDATION-OWNERSHIP.md`.

Schemas, tables and columns are never written by hand here. They are authored as Dryv contracts (`dryv/contracts/apps/database`) and generated by the project packs `dryv/packs/rust-models` and `dryv/packs/rust-sql` into this folder.

## Rust workspace (foundation, in progress)

```text
Cargo.toml                    workspace
crates/mzizi-db-core          config, two bounded SQLx pools, typed ids, fail-closed auth,
                              named domain operations (the only hand-written SQL)
crates/mzizi-db-generated     rust-models pack output; never hand-edited
crates/mzizi-db-service       Axum HTTP service, default port 3303 (MZIZI_DB_SERVICE_PORT)
crates/mzizi-db-cli           admin binary: assemble, plan, migrate, status, verify, roles (seed: not implemented)
generated/sql                 rust-sql snapshots (main.sql, operations.sql); input to `mzizi-db assemble`
migrations/main               assembled, checksummed SQL releases for `mzizi` (+ .snapshot record)
migrations/operations         assembled, checksummed SQL releases for `mzizi_operations`
tests/                        migration, auth and reference integration tests
```

- Two separately bounded connection pools with separate credentials; administrative credentials are loaded only by the CLI binary. The service binary cannot run DDL.
- Migrations serialize with per-database advisory locks; each release commits together with its `public.mzizi_migrations` ledger entry; changed checksums and wrong target identities are refused.
- Service callers are authenticated; authorization is resolved and enforced in Rust and fails closed. Callers never supply SQL or table names.
- Build and test with `cargo check` / `cargo test` from this folder, or through the repository-root Bun runner once wired.

Regenerate with `dryv generate` from the repository root, then `mzizi-db assemble --target main|operations`. Live tests run only when `MZIZI_DB_TEST_SERVER_URL` points at the isolated instance (they create and drop one `mzizi_test` database). `roles` needs `MZIZI_DB_SERVICE_PASSWORD`.

The foundation targets a fresh isolated local PostgreSQL instance holding `mzizi` and `mzizi_operations`. It ships no destructive reset command and preserves existing development databases and object storage.

## Legacy Bun TypeScript service (transitional)

The previous service (`src/`, `package.json`) keeps its current behavior on port `3301` until its callers migrate: status/migration/seed/verify CLI for the disposable `mzizi_new` database and the named internal HTTP operations used by the API, engine and filesystem callers. Its commands still run through the root runner: `bun run db status`, `bun run db migrate`, `bun run db seed`, `bun run db verify`. Its administrative connection is `MZIZI_DATABASE_URL`; the service uses `DATABASE_RUNTIME_URL`; the NestJS API uses a separate read-only `DATABASE_URL`.

Known gaps, still tracked: some Python filesystem metadata and manifest-sync paths connect to PostgreSQL directly; and the Python workspace references a `mzizi-database` package that does not exist in `source/packages/` — the generated Python HTTP client is a distinct package and does not fill that slot.

## Generated scope and engine requirements

All Main domain groups (reference, geography, legal, official, governance, politics, finance, civic, source, filesystem) and the operational groups are generated: 81 `mzizi` tables and 46 `mzizi_operations` tables. Notes:

- The `geometry` column of `geography.geometries` is a Dryv placeholder (`dryv.unknown()`) and is excluded from both the SQL and the Rust model until PostGIS storage is designed.
- Invariants render recursively into `CHECK` constraints, up to five levels deep; comparisons against `null` become `IS [NOT] NULL`. This needs a Dryv engine where a null comparison types as boolean (a small local change in `source/engine/python/engine/.../validation/common/expressions.py`; the pinned commit in `dryv.yaml` does not contain it yet).
- Database names are deployment choices; the logical targets are `main` (`mzizi`) and `operations` (`mzizi_operations`) and the ledger records the logical identity. A working remote setup used `mzizix` and `mzizix_operational` through `MZIZI_DB_MAIN_ADMIN_URL` and `MZIZI_DB_OPERATIONS_ADMIN_URL` kept in the git-ignored `.data/`.
- Run only the model/table contract test (`generated_models_match_live_tables`) against shared servers; the lifecycle test creates a cluster-wide `mzizi_service` role.

## Canonical Dryv store ownership

The database authoring app now owns two canonical stores, `main` and `operations`, with explicit
read/write access and provided auth/reference operations. Placement is defined on the neutral
schema groups, not mirrored namespace lists in pack inputs. Root usage supplies physical names
and the existing runtime/admin environment variable names. The legacy NestJS contracts remain
independent.

Use repository-root `bun run dryv:database:plan`, `dryv:database:generate` and
`dryv:database:verify`; append `-- --store main` or `-- --store operations` for a partial run.
Perform one complete database generation first to create stable shared catalogue modules.
Separate model activations own `models/main/` and `models/operations/`, while Rust public module
paths remain unchanged. Store-specific verifiers combine through the stable generated contract
module. SQL snapshots keep the existing `main.sql`/`operations.sql` locations. Non-persisted
Accountability indicators do not become tables or acquire a database assignment.

Schema snapshot regeneration does not assemble or apply a migration. Existing releases, `.snapshot`
checksums, target identity checks and the public ledger are unchanged. Do not switch this project
to `dryv migrate` until the Mzizi storage mappings and an explicit ledger-adoption procedure are
reviewed. See [contract workflow](../../../dryv/README.md) for approval and checkpoint commands.

Fresh Rust generation requires the workspace rust_decimal dependency and SQLx rust_decimal
feature for exact NUMERIC columns. The SQL pack renders canonical CHECK expressions, filtered
indexes, composite foreign keys, same-scope keys, exclusion constraints and acyclic triggers;
unsupported mappings stop generation. Existing release files are never overwritten by this step.
