# Mzizi API (NestJS)

The Mzizi product API. It reads and serves canonical data and accepts comments, evidence references and role-gated review decisions. It does not connect to the database with a write role: those three operations are sent to named endpoints on `source/backend/database`. It does not scrape, clean, extract, migrate or seed.

Nearly everything under `src/modules`, `src/types`, `src/app.module.ts` and `src/database` is generated by Dryv from the contracts in the repository-root `dryv/` folder, using the same structure and packs as the Alidantech backend. Files marked "Scaffolded by Dryv once" (use cases, service implementations, `database.module.ts`, `vitest.config.ts`) belong to the project and are where hand-written logic goes. See `dryv/README.md` for the generation workflow. The inherited Python service lives in `source/backend/api-legacy`.

## Run it locally

Start the local PostGIS container (the shared `postgis` container on 127.0.0.1:5432), migrate the disposable `mzizi_new` database with the TypeScript database CLI, and start both services:

```bash
docker start postgis
export MZIZI_DATABASE_URL=postgres://postgres@localhost:5432/mzizi_new
bun run db reset --confirm mzizi_new
bun run db provision-local-roles
AUTH_BOOTSTRAP_ISSUER=https://issuer.example AUTH_BOOTSTRAP_SUBJECT=your-oidc-sub AUTH_BOOTSTRAP_NAME="Local admin" bun run db bootstrap-admin
cd source/backend/database && bun install
DATABASE_RUNTIME_URL=postgres://database_runtime@localhost:5432/mzizi_new DATABASE_SERVICE_TOKEN=local-development-token DATABASE_PORT=3301 bun run start
cd source/backend/api && bun install
export DATABASE_URL=postgres://api_reader@localhost:5432/mzizi_new
export DATABASE_SERVICE_URL=http://127.0.0.1:3301
export DATABASE_SERVICE_TOKEN=local-development-token
bun run start          # http://localhost:3000, 167 routes, e.g. /v1/reference/jurisdictions
```

The TypeScript database CLI supports status, migration, reset, auth/reference seed loading, local runtime-role provisioning, first-admin bootstrap, and pipeline release propose/activate operations. Do not use the old Python `db:init` or `db:reset` entrypoints for this target architecture.

## Test

```bash
bun run typecheck
bun run test                                                                  # generated specs; PostgreSQL suites skip without TEST_DATABASE_URL
TEST_DATABASE_URL=postgres://postgres@localhost:5432/postgres bun run test    # adds the PostgreSQL suites (they create their own scratch databases)
```

## Database access

`DATABASE_URL` must point at a role with SELECT only on the domain tables. `synchronize` is false and the API has no migration path. Audit writes use `DATABASE_SERVICE_URL` and a shared internal service token; the TypeScript database service owns those writes.

## Authentication and writes

Reads are public. The only writes are the three `POST /v1/audit/*` routes (comments, evidence submissions, review decisions).

- **Rules come from the contracts.** The generator does not wire contract policies into guards, so `dryv/tools/export-access.ts` exports each operation's policy to `src/auth/access-rules.generated.ts` (`bun run access:export` in `dryv/`; `access:check` is part of `bun run check`). The global `AuthGuard` enforces them and `ActorInterceptor` carries the verified actor to the use case, installed in `main.ts` with `installAuth`.
- **Tokens.** Bearer JWTs from an OIDC-compatible issuer (`AUTH_ISSUER`, plus `AUTH_JWKS_URL` or a PEM `AUTH_PUBLIC_KEY`). `sub` must be a uuid and is the actor id; the highest of the `roles` claim (reader, contributor, reviewer, admin) is the role. With authentication unconfigured a protected route answers 503, never open access.
- **Actor and role never come from the body.** Use cases stamp `actorId` / `reviewerId` from the token; the validation pipe also strips unknown body fields.
- **Database owner.** `src/database/write-database.ts` calls named database-service operations for comments, evidence references, and review decisions. The API's verified actor id is sent with each command; the database service is bound to loopback and validates the service token.
- **Targets.** `targetKind` must be one of the evidenced entities' schema-qualified tables (for example `geo.units`) (from the same export) and the record must exist; comment replies must be on the same record.
