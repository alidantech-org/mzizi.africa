## 2. Hidden dependencies found in the removal of `admin`

The audit of references found that `admin` is not only a UI:

- **Development sign-in.** `admin/scripts/dev-env.ts` creates the RS256 key pair under `.dev/secure/dev-auth` and signs tokens for the seeded reviewer and admin accounts; the NestJS API verifies them with the public key (`scripts/tasks/setup.ts` runs it as "Development sign-in keys"). Removing `admin` removes the only issuer of local tokens. A replacement is needed first: a `dev`-side or script-side token issuer, or the real OIDC provider.
- **Data catalog.** `admin` has a `catalog` script that generates `src/lib/review/data-catalog.ts` (run by `scripts/tasks/dryv.ts` as "Web data catalog") and a test that follows the generated catalogue (`ec7b926c`).
- **Review workbench.** Routes under `admin/src/app/review` (assessments, candidates, captures, checks, data, documents, jobs, runs, sites, structure) and `admin/src/app/admin` (scraper, storage and file explorer, catch-all pages). The review path (raw artifact, extraction, candidate, review) is a product rule; its UI must exist somewhere (`dev`), or its loss is accepted explicitly.
- **Root scripts.** `scripts/lib/projects.ts` (two entries each), `scripts/tasks/setup.ts` (cache paths and sign-in step), `scripts/tasks/dryv.ts` (catalog step), `scripts/README.md`.
- **Contracts and generation.** `dryv/contracts/apps/admin/index.ts` is declared but not in `dryv.yaml`.
- **Documents** naming the apps: `AGENTS.md`, `.docs/docs/{SYSTEM,STORY}.md`, `.docs/design/architecture/{DEVELOPER_PORTAL,MIGRATION,DATA_LIFECYCLE}.md`, `.docs/design/operations/{repository-map,development-setup}.md`, `.docs/_plan/guides/independent-data-pipelines.md`, `source/apps/app/README.md`, the 2026-11-17 handoff and the completed Task records (history, left as is).

## 3. Method to make the radius exact (before any migration task)

1. Parse the Dryv IR (`dryv/.dryv/ir/*.ir.yaml`) and the generation outputs to list generated files with their source.
2. Build an import graph per app and the call graph from pages to SDK operations.
3. Label each file: `generated`, `scaffolded-once`, `hand`, `dead`, `removed`.
4. Commit the table under `.docs/design/operations/`, regenerated by a script; a contract change prints the files and labels it touches.
5. Re-measure the estimates below from the table.

## 4. Migration order

1. Settle the open questions in the design documents; agree the page-by-page address map.
2. Provide the replacement for the dev sign-in issuer; record the review workbench; then remove `admin` and old `mobile` with every reference (see section 5).
3. Dryv capabilities and the proving slice (place overview with context).
4. Context, copy, preference and indicator data in schemas; composed reads replace `reads/*.ts` one document at a time.
5. Web migrated feature by feature behind the same addresses; Flutter app in parallel by feature; `dev` including the review workbench.
6. Delete dead generated demo pages, hand parsers, constants and fetch code; turn on the gates; update `AGENTS.md`.
7. Interactions (likes, views, posting) after the privacy and legal review is complete.

## 5. Removal procedure (deferred and removed)

**Done on 2026-11-18** (owner confirmed): `source/apps/admin`, `source/apps/mobile` and `dryv/contracts/apps/admin` were deleted, root script entries and document mentions rewritten. **Known consequence:** local development sign-in keys are no longer created by `setup` and nothing issues local API tokens, and the review workbench is gone until rebuilt in `dev`. The `catalog` command now only regenerates the Dryv system catalogs. The steps below describe what was done.

- Record first (this document, section 2), then delete `source/apps/admin`, `source/apps/mobile`, `dryv/contracts/apps/admin`, and the entries in `scripts/lib/projects.ts`, `scripts/tasks/setup.ts` and `scripts/tasks/dryv.ts`, and the workspace entries in lockfiles and `package.json` workspaces if present.
- Replace every document description with: "Deferred and removed on 2026-11-18. The `dev` portal is the administrative interface until an admin app is funded." Do not leave stale paths.
- Run `uv run mzizi-manifest check`, `task validate`, and `bun run check` to confirm nothing still imports them.
- Deletion is permanent in the working tree and recoverable only through git history, so the owner confirms immediately before it runs.

## 7. Rollback

Each phase ends on a green gate and a commit on `develop`. Generated output is reproducible from contracts; hand components stay in `source/ui`. The removed apps stay in git history. A phase can be reverted by `git revert` of its commits; schema migrations are additive and immutable, so a rollback leaves unused tables rather than data loss.
