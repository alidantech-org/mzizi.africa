# Frontends are contract-first, SDK-only, multi-country and context-driven

## Owner update: handwritten web and generated backend boundary

The owner revised web ownership on November 20, 2026. For the current web stage, rules 1 and 3 below no longer require generated UI: pages, themes, navigation, components and server-rendered screen assembly are handwritten. Dryv still owns backend schemas, request/response validation, transport signatures and the shared API bridge client. Typed project-owned backend composition is permitted behind those generated signatures. App and dev frontend generation is unchanged.

The real web has an anonymous welcome-page setup dialog and canonical country-prefixed place routes; `/demo` remains permanently isolated until the owner requests removal. An explorer request requires an explicit country rather than silently selecting a default country. Device location provides candidates for confirmation, and saved preferences do not override the country/place address. This supersedes rule 6 for the real explorer. Product reads run on the server through generated feature helpers; browser location and approved preference writes remain explicit server actions. The first implementation covers registered geography and recorded coverage, not every subject shown in the demo.

## Earlier decision, retained for context

Recorded from the owner's statements on 2026-11-18, after the audits in [HANDOFF-FRONTEND-CRITIC-20261118](../handoffs/HANDOFF-FRONTEND-CRITIC-20261118.md) and [HANDOFF-HARDCODING-AND-CONTEXT-AUDIT-20261118](../handoffs/HANDOFF-HARDCODING-AND-CONTEXT-AUDIT-20261118.md). It supersedes [DEC-FRONTEND-ASSEMBLY-20261117](DEC-FRONTEND-ASSEMBLY-20261117.md), whose rule that "implementation is hand-written" is rejected.

1. **Everything is authored in Dryv.** Schemas, operations, queries and the behaviour of backend and frontends are authored in `dryv/contracts/apps` and `dryv/contracts/schemas` and generated by packs. Hand-written code is limited to visual components in `source/ui`.
2. **SDK only.** Every frontend request goes through the generated SDK client. No hand-written `fetch`, no Next.js route handlers invented by the app, no UI-side assembly of several endpoints. A screen has one authored composed read.
3. **Dryv is improved, not worked around.** Anything Dryv cannot express becomes a Dryv change (built directly, recorded and tested), never a hard-coded UI fallback.
4. **Server rendering by default.** Pages are server components that fetch on the server; `"use client"` belongs only to leaf components.
5. **Multi-country now.** Country is a dimension of the data and of every context-dependent read; no country, currency, level or indicator literal in apps or reads.
6. **Country from the Cloudflare `CF-IPCountry` header**, trusted only from the Cloudflare edge, with an authored development override. Context resolution order: selection, preference, device position, CDN header, default.
7. **Interface copy lives in the database per language**, with keys authored in contracts.
8. **Mobile reference.** The Flutter app follows the RideRescue driver pattern: generated SDK and UI kit, Riverpod, services and repositories.
9. **`apps/admin` and the old `apps/mobile` are deferred and removed.** The `dev` portal is the administrative interface until investors fund an admin app. The Flutter `apps/app` stays and is the mobile app.
10. **User interactions (owner direction, under legal review):** the server stores interactions without accounts using a device identity. The web allows likes and views only; the mobile app alone allows comments, evidence, opinions and images, each with GPS proof and a device fingerprint, and content filtering. See [USER_INTERACTIONS_AND_TRUST](../design/architecture/USER_INTERACTIONS_AND_TRUST.md); this item is a direction to be designed, not an approved build.
11. **Documentation precedes code.** Design documents are written and agreed before implementation tasks are created.
