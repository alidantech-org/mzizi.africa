# Frontend critic and handoff (2026-11-18)

**Status: nothing has been fixed. This is the record of an audit, and the agenda for the owner and the next agent to agree on before any more frontend work.**

## 1. What the owner required

1. Every schema, operation, query and piece of frontend or backend behaviour is **authored in Dryv contracts** (`dryv/contracts/apps`, `dryv/contracts/schemas`) and **generated by packs**.
2. Frontends reach the backend only through **generated client SDKs**. No hand-written `fetch`, no invented Next.js route handlers.
3. Whatever Dryv does not yet expose is fixed by **improving Dryv or the packs**, never by hard-coding in the UI.
4. Next.js pages are **server-rendered**: default and most interactive reads are fetched and painted on the server. `"use client"` belongs only to leaf client components.
5. Mobile copies the **RideRescue** pattern: SDK client plus UI kit, Riverpod state, generated fetch patterns.
6. An app is described by **features, behaviours and intents** authored in contracts, not by one `index.ts` that declares a handful of views.

Reference projects that show the intended result: `~/Projects/work/riderescue/riderescue/{dashboard,driver}` and `~/Projects/work/SierreTechnologies/defytickets/{events,backend}`.

## 3. What went wrong (findings)

Scope of the audit: structure, counts and sampled files in `dryv/`, `source/apps/{web,admin,www,dev,app,mobile}`, `source/ui`, `source/sdk`. It is not a line-by-line review; each finding states what was checked.

### F1. Intent was authored for six screens; the product has dozens

`dryv/contracts/apps/web/index.ts` and `app/index.ts` declare FeatureBrowse, FeatureDetail, PlaceSearch, PlaceProfile, SourceBrowse, EvidenceView. The actual web app has routes for leaders, elections, parties, parliament, motions, tenders, civic, projects, statistics, leaderboards, saved, browse and a home dashboard. None of these exist in any contract. They were written by hand and the contracts were never extended. The API contract `dryv/contracts/apps/api/insights.ts` (476 lines) exposes the operations; no app contract says which feature, behaviour or intent uses them.

### F2. One `index.ts` per app, no features or behaviours

Each app is one file with one `dryv.group`, one feature called "Features" and a flat list of views. Intents such as "compare my place with the country", "follow the leader tree", "keep a place", "switch language or theme", onboarding, search, and navigation are not modelled. The files even say "First slice only ... to inspect what generation produces" and were never taken past that.

### F3. The decision that justified this contradicts the owner's stated requirement

`DEC-FRONTEND-ASSEMBLY-20261117` (marked "owner-approved") says "Dryv holds intent and behaviour; **implementation is hand-written**", "`admin` and `mobile` are hand-written and untouched", and scaffolded pages "belong to the app". This is the opposite of requirements 1, 3 and 5. Either the approval was narrower than recorded or it was over-read. **The owner must confirm or reject this decision before anything else is built.** This critic treats it as disputed.

### F4. Client-side rendering and client-side fetching everywhere

- `web/app/*/page.tsx`: 25 of 27 are `"use client"`, wrap a body in `<Suspense>`, read `useSearchParams()` and fetch in the browser through `useAsync`. Example: `web/app/leaders/page.tsx`, `web/app/place-profile/page.tsx`.
- The pack template `dryv/packs/app-next` (`lib/dryv/transport.ts.j2`, `components/dryv/pages/{list,detail}-page/page.tsx.j2`) **generates the client pattern**: generated pages start with `"use client"`, use `useEffect` or `useState`, and call a browser `fetch`. The bad pattern is in the pack, so every regeneration reproduces it. Server actions or server-side SDK calls (as in RideRescue `_gen/server/actions`) are not generated.
- `NEXT_PUBLIC_API_URL` makes the API base visible to browsers and forces CORS configuration (the runner builds an allow-list for it).

### F5. Hand-written fetches and invented Next.js routes

- `dev/app/api/engine/[...path]/route.ts`: a hand-written proxy route with a hard-coded allow-list (`capabilities`, `health`, `v1/jobs`, ...) and a hard-coded default engine URL. The file says "Scaffolded by the project, not Dryv."
- `dev/lib/portal/engine.ts`, `dev/lib/portal/explore.ts`, `dev/components/portal/viewer.tsx`: direct `fetch`, "health document (not yet in the contract)".
- `admin/src/lib/review/api.ts`: a hand-written `api<T>(path, init)` wrapper with a default `http://127.0.0.1:8700`, plus `admin/src/lib/review/oidc.ts`, `admin/src/lib/system/overview.ts`, `admin/src/server.ts`, `admin/src/contexts/UploadContext.tsx`, `admin/src/components/admin/storage/files/FilePreviewDialog.tsx`, and two route handlers under `admin/src/app/review/auth`.
- `web/lib/site/insights.ts` (779 lines) and `web/lib/site/api.ts` wrap generated request builders by hand and re-type the sections the API marks `dynamic`. This is a Dryv gap (typed unions or schemas for those sections) patched in the app.

### F6. `admin` and `mobile` were abandoned as hand-written

- `source/apps/admin`: 106 client files, own `components.json`, own UI kit, a `json/` folder and a hand-written fetch layer. Its contract (`dryv/contracts/apps/admin/index.ts`) is one list view and is not in `dryv.yaml`'s authoring sources.
- `source/apps/mobile`: 6.6k lines of hand-written Dart using `package:http` and `geography_api.dart`, no SDK, no Riverpod, a separate theme.
- `source/apps/www`: one page; nothing wrong in principle, but it is outside the contract and theme flow.

### F7. Generated and hand-written pages exist in parallel and drift

`web/components/dryv/pages/web/*/page.tsx` (generated: generic `Record<string, unknown>` tables with machine-derived column labels such as "Feature Id") sit beside `web/app/*/page.tsx` (hand-written, "Scaffolded by Dryv once; this file belongs to the app"). The generated pages are dead code that look like the product. Generation runs with `--conflicts keep`, so pack improvements never reach the hand-edited files.

### F8. Flutter `app` does not follow the RideRescue structure

- The SDK and Riverpod are in `pubspec.yaml`, but state is partly Riverpod (`languageProvider`) and partly singletons: `UserStore.instance` consumed through `ListenableBuilder` in `main.dart`, `SavedStore` with `SharedPreferences`. RideRescue uses providers consistently with `core/services`.
- About 3.0k lines of insight screens (`insights/civic_pages.dart` 614, `democracy_pages.dart` 776, `explore_pages.dart` 587, `kit.dart` 731) are hand-written.
- Hard-coded visual and text values: 45 `Color(0x..)`, `Colors.` or `fontSize:` uses outside the generated theme, and `presentation/i18n/strings.dart` (219 lines of hand-keyed strings). 22 uses of `StatefulWidget` or `FutureBuilder`.
- `pubspec_overrides.yaml` points at an absolute path on one machine, still unresolved from the previous handoff.
- Many `app` files have uncommitted edits (git status at audit time), so the state is not even recorded.

### F9. Hard-coded product and place knowledge in the UI

"Kenya" appears in titles, labels and fallbacks (`hero-title`, `browse-view`, `leader-tree`, `fact-strip`, statistics page); "KSh" formatting and "47 counties" are in `lib/site/format.ts` and `components/site/ui/primitives.tsx`. This breaks the rule that jurisdiction knowledge lives in manifests, seed data or database records, and blocks the multi-country goal.

### F10. The pack source and pin are fragile

`dryv.yaml` pins the official packs as `file:///home/alidante/Projects/personal/alidantech-org/codepot/packs` (one machine, local path) and the previous handoff warns that a full regeneration rewrites `app.module.ts` and drops hand-added modules. Regeneration is not reproducible from a clean checkout.

### F11. Process and record

- The handoff declared the feature "closed" while the dev portal was "a stub", the bridge fix was uncommitted, transitions had no context bindings and the real screens were not in contracts.
- Status layers were not separated as RideRescue does: contract exists, generated, wired, validated.
- No task or record states which parts may be hand-written.

### What is acceptable and should be kept

Generated API and SDK pipeline for `api` exists and works (`source/sdk/api-ts`, `api-dart`); `web/lib/site/api.ts` and `app` use generated request builders rather than raw URLs in most places; `www` and the brand assets are small; the NestJS API itself is generated into `source/backend/api/src/modules`. The theme contract (`dryv/contracts/schemas/theme.ts`, packs `theme-css`, `theme-dart`) is the right idea.

## 4. Proposed split to agree (not decided)

| Layer | What belongs there | Examples from today's code |
| --- | --- | --- |
| **Dryv contracts** (`dryv/contracts/apps/<app>/`, several files per app: features, views, behaviours, intents, navigation, state, i18n keys) | Every screen and flow, which operation each part consumes, context bindings, transitions, loading/empty/error behaviour, which parts render on the server, user preferences (language, theme, saved items) as authored state, copy keys, place-agnostic labels | All 27 web routes, the Flutter onboarding and tabs, the leader tree, compare, rankings, saved items, language and theme switches |
| **Dryv contracts** (schemas and api) | Typed `dynamic` sections of insights responses; engine health and explore operations; any query the pages need | `insights.ts` typing done by hand in `web/lib/site/insights.ts`; engine `/health` and explore reads |
| **Packs** (`dryv/packs/app-next`, `app-flutter`, `sdk-*`, new ones) | The patterns: server-component pages with server-side SDK calls and `searchParams`, form actions, a server-only SDK instance, route/layout/loading/error files, Flutter providers and repositories, routers, app shell, state management per RideRescue, generated i18n and theme | Replace the browser `transport.ts` and `"use client"` page templates; add server-action style templates |
| **Generated** | Everything the packs emit, never edited: SDKs, per-view pages and screens, routers, providers, request builders, types, theme, copy | `lib/api`, `lib/types`, `components/dryv/*`, `_gen`-like folders; no hand edits and `--conflicts` policy that cannot silently keep drift |
| **Hand-written source** (small, named, in `source/ui/*` or marked slots) | Visual components the generated screens assemble, charts, maps, the globe, hemicycle, tree and ramp widgets, complex interactions Dryv cannot describe; typed props only | `source/ui/web`, `source/ui/flutter`, `components/site/ui/hemicycle.tsx`, `cinematic_globe_map.dart` |
| **Auth/OIDC for the admin review login** | To be decided: is this generated from an auth contract or a legitimate hand-written server concern | `admin/src/app/review/auth/*`, `lib/review/oidc.ts` |

## 5. Questions that block the fix (owner decisions)

1. **DEC-FRONTEND-ASSEMBLY**: is "implementation is hand-written" rejected? If so it is superseded, not edited, by a new decision.
2. How are server rendering and the SDK united: Next.js server actions that call the SDK, or server components calling a generated server-only SDK client? RideRescue uses generated `'use server'` actions; DefyTickets uses a server SDK. Which does Mzizi adopt?
3. Where does the browser need direct API access (live maps, polling) and how is that generated without `NEXT_PUBLIC_API_URL`?
4. How much of behaviour and state does Dryv model (intents, transitions, preferences, saved items, i18n) versus a pack convention? Which Dryv engine changes are in scope (this is the project's own Dryv checkout)?
5. Are `admin` and `mobile` to be regenerated from contracts, or retired and replaced by `app` and a rebuilt admin? What happens to `www`?
6. The dev portal engine proxy: generated BFF in a pack, or an engine contract exposed to server-side calls only?
7. Which RideRescue and DefyTickets files are the template to copy first (suggest: dashboard `app/(app)/bookings/page.tsx`, `_gen/server/actions/*`, `driver/lib/presentation/screens`, `driver/lib/core/services`)?
8. Pack source: publish the packs repository or vendor them so regeneration reproduces on a clean checkout.
