# Typed NestJS persistence

This opt-in pack generates a use case per HTTP operation with a declared query or mutation, plus a PostgreSQL runtime for TypeORM. Bind `schema.validation` to class-validator DTOs. Bind its `operation.usecase` provider into the official NestJS server pack. Configure the destination imports alias as shown in the fixture. Register `PersistenceRuntime` with an explicit factory over `new StoreConnections(new Map([[canonicalStoreName, new TypeOrmConnection(selectedDataSource)]]))` and register a request-scoped `PersistencePolicyResolver` that evaluates the operation's declared policies; no global connection, migrations or schema synchronization run at application startup.

The Engine owns the validated, named persistence plan. The pack embeds that plan as a TypeScript literal checked with `satisfies Plan`; templates do not parse JSON or expand nested selections to a fixed depth. The runtime renders SQL locally and binds all data values. Canonical quoted storage names and the explicit snake/camel column option control identifiers. Recursive correlated selections support nested to-one/to-many results and counts without root-row duplication. Reads enforce trusted policy scope, ordering, missing failures, bounded windows and separate total counts. Composite relation companions are projected as typed join pairs, so country-partitioned nested selections do not join on a partial key. Geometry fields use GeoJSON at SRID 4326; other SRIDs require an explicit adapter. Outputs pass through generated DTO validation.

The runtime requires a `TrustedContext`. Generated use cases resolve it through the injected request-scoped `PersistencePolicyResolver`, or accept an explicit trusted second argument for application orchestration. The application policy adapter supplies the principal and declared policy values; controllers must never populate it from request bodies. Policy scope is conjoined with ordinary selectors and cannot be overwritten by mutation inputs. Missing policy values fail closed. All input and policy values participate in cache keys, including country and language when declared by the application. The principal always participates. Project contracts own language fallback and localized response schemas.

Writes support explicit create, update, hard-delete and soft-delete assignments, omitted versus null patches, generated UUID/time assignments, database defaults, returning projections, missing failures and SQLSTATE failure mappings. Every write runs inside an owned TypeORM transaction, including multi-row rejection rollback. Caller-managed transactions are deliberately not accepted: commit and cache invalidation belong to the same runtime boundary. Cache generations increment only after successful commit. A concurrent read may populate an old generation, which later reads cannot reach. Cache transport failures propagate; applications must choose their retry/idempotency policy explicitly.

`RedisCache` takes a tiny command adapter and a required project/store prefix. Adapt an existing Redis client's raw command method, without exposing its untyped replies elsewhere. TTL uses Redis `EX`. Invalidation increments an operation generation; no wildcard deletion is required. Pack registration, the Redis client and policy evaluation are application-owned.

`PersistenceContext.selections` also exposes preorder identities and parent indices for packs that prefer generating individual nested loaders. This finite context has no template nesting cap. `document` remains the full typed-plan transport for runtime interpreters.

The runtime fails on unsupported canonical operators instead of silently substituting SQL. It does not execute durable events, retries, workflows or geometry transformations. Those require explicit runtime infrastructure; table descriptions and partition DDL remain owned by the SQL migration pack.

Async execution, retries, idempotency, required audit and emitted events are explicit runtime feature requirements in the typed plan. This pack rejects unsupported requirements before executing SQL. TSK-1CBB67459735 tracks durable execution separately from layout generation.

Canonical named stores are dispatched through `StoreConnections`; missing registrations fail before SQL. A direct connection is accepted only for unscoped fixture plans. Store identity also participates in cache keys. Applications register the connection map explicitly; the runtime never guesses a database from schema names.
